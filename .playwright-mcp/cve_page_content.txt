ESO runs as a controller in the cluster and syncs secrets from AWS into Kubernetes Secret objects on a configurable schedule (typically 1-5 minutes).\n\nInstall ESO via Helm:\n\nhelm repo add external-secrets https://charts.external-secrets.io\nhelm install external-secrets external-secrets/external-secrets   -n external-secrets --create-namespace\n\n\nEach microservice gets its own SecretStore or you use a shared ClusterSecretStore pointed at AWS Secrets Manager:\n\napiVersion: external-secrets.io/v1beta1\nkind: ClusterSecretStore\nmetadata:\n  name: aws-secrets-manager\nspec:\n  provider:\n    aws:\n      service: SecretsManager\n      region: ap-south-1\n      auth:\n        jwt:\n          serviceAccountRef:\n            name: external-secrets-sa\n            namespace: external-secrets\n\n\nThen each service defines an ExternalSecret that pulls only its own secrets:\n\napiVersion: external-secrets.io/v1beta1\nkind: ExternalSecret\nmetadata:\n  name: payments-db-credentials\n  namespace: payments\nspec:\n  refreshInterval: 2m\n  secretStoreRef:\n    name: aws-secrets-manager\n    kind: ClusterSecretStore\n  target:\n    name: payments-db-credentials\n    creationPolicy: Owner\n  data:\n    - secretKey: db_password\n      remoteRef:\n        key: /prd/payments/db\n        property: password\n\nPer-Service Isolation with IRSA\n\nEach microservice gets a dedicated Kubernetes ServiceAccount mapped to its own IAM role via IRSA (IAM Roles for Service Accounts). The IAM policy on each role is scoped to exactly the secrets that service needs - nothing broader.\n\neksctl create iamserviceaccount   --name payments-sa   --namespace payments   --cluster prod-cluster   --attach-policy-arn arn:aws:iam::123456789012:policy/PaymentsSecretsPolicy   --approve\n\n\nThe IAM policy uses a resource-level condition to restrict access:\n\n{\n  \"Effect\": \"Allow\",\n  \"Action\": [\"secretsmanager:GetSecretValue\", \"secretsmanager:DescribeSecret\"],\n  \"Resource\": \"arn:aws:secretsmanager:ap-south-1:123456789012:secret:/prd/payments/*\"\n}\n\n\nThe pod spec references this service account - and only this service account - so even if a payments pod is compromised, the blast radius is limited to /prd/payments/* secrets.\n\nRotation Without Downtime\n\nSecret rotation is where most teams introduce unnecessary downtime. The correct model is: rotate in AWS Secrets Manager, let ESO sync the updated value into the Kubernetes Secret, and have the application pick up the change without restarting.\n\nTwo practical approaches:\n\n1. Secret volume mount with inotify or periodic reload\n\nMount the secret as a file (not an env var - env vars are baked at container start). Applications like Nginx or Envoy can reload config on SIGHUP. For custom services, implement a reload endpoint or a goroutine/thread that re-reads the file every 60 seconds.\n\nvolumeMounts:\n  - name: db-credentials\n    mountPath: /etc/secrets\n    readOnly: true\nvolumes:\n  - name: db-credentials\n    secret:\n      secretName: payments-db-credentials\n\n\n2. Secrets Store CSI Driver (for direct AWS integration)\n\nThe CSI driver mounts secrets directly from Secrets Manager into the pod filesystem and supports auto-rotation via the rotation flag. When Secrets Manager rotates a secret, the mounted file updates without pod restart within the rotationPollInterval.\n\nparameters:\n  objects: |\n    - objectName: /prd/payments/db\n      objectType: secretsmanager\n      objectAlias: db_password\n  rotationPollIntervalInSeconds: \"120\"\n\n\nAvoid injecting secrets as environment variables for anything that rotates - you will always need a pod restart to pick them up.\n\nAudit and Alerting\n\nAll Secrets Manager API calls appear in CloudTrail automatically - no configuration needed. Enable CloudTrail in your account if it is not already running.\n\nFor rotation, enable AWS-managed rotation on each secret:\n\naws secretsmanager rotate-secret   --secret-id /prd/payments/db   --rotation-lambda-arn arn:aws:lambda:ap-south-1:123456789012:function:RotateDbPassword   --rotation-rules AutomaticallyAfterDays=30\n\n\nSet up CloudWatch Metric Filters to alert on anomalous access patterns - for example, GetSecretValue calls from unexpected IAM principals or unusually high call volumes:\n\naws cloudwatch put-metric-alarm   --alarm-name secrets-unusual-access   --metric-name CallCount   --namespace AWS/SecretsManager   --statistic Sum   --period 300   --threshold 50   --comparison-operator GreaterThanThreshold   --alarm-actions arn:aws:sns:...:security-alerts\n\n\nAWS Security Hub and GuardDuty also surface anomalous Secrets Manager access (e.g., access from a Tor exit node or from an unexpected region) with no custom logic required.\n\nSummary\n\nThe complete flow is: Secrets Manager holds the source of truth, IRSA scopes each service's read access to its own path, ESO syncs on a 2-minute interval into namespaced Kubernetes Secrets, pods mount secrets as files so rotation is picked up without restarts, and CloudTrail provides a full audit log with CloudWatch alerts watching for spikes or unexpected principals.\n\nDID YOU KNOW THIS?\n\nKnew it\nNeed to review\n\nAnswers may include AI-assisted content and should be verified independently.\n\nReport incorrect answer\nAsked at\n\nCompanies where this question has been reported\n\n+ Report a company\n\nNo company reports yet.
